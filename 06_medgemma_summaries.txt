TASK: Implement Workflow 06 — On-device summaries with Gemma 3 and MedGemma

Read `rules.txt` first and follow the architecture established by `00_init_workflow.txt`.

This task replaces the mock summary function with real on-device LLM inference
via MLX, and adds model management to Settings.

Do not redesign unrelated screens or bypass the Domain/Data/Services architecture.

--------------------------------------------------
PURPOSE
--------------------------------------------------

Tangent currently fakes its summaries. When a recording finishes, the transcript
is produced on device and `RecordHomeViewModel.summarize(_:)` takes the first
sentence of it as `DIARY.summary_short`, with the whole transcript stored as
`DIARY.summary_long`.

This workflow replaces that with a real language model running entirely on
device: the transcript plus the patient profile go in, and two first-person
summaries come out as JSON — a one-sentence `short_summary` and a dense
`long_summary` paragraph.

Everything stays on the device. The only network traffic this workflow adds is
the one-off model download from the Hugging Face hub, and it only happens when
the user explicitly asks for it in Settings.

--------------------------------------------------
DECISIONS ALREADY MADE
--------------------------------------------------

These were chosen by the project owner. Do not revisit them.

1. Ship BOTH models. The user picks one in Settings, and picking it is what
   downloads it.
2. Use plain generation plus JSON parse-and-retry. Do NOT use
   MLXGuidedGeneration / grammar-constrained decoding. It only exists on an
   unreleased `main` of mlx-swift-lm and would force an unpinned dependency and
   vendored C++ into the app.
3. Model downloads are managed in Settings, and the rows are labelled with the
   model's own name ("Gemma 3 1B", "MedGemma 4B"). Never call it "the summary
   model" in the UI.
4. When the model cannot run — Simulator, not downloaded, load failure, model
   returned unparseable output — fail explicitly. Show the error and a retry
   action. Do NOT silently fall back to a mock summary.

--------------------------------------------------
MODELS
--------------------------------------------------

Two options, both 4-bit:

  Gemma 3 1B
    id: `LLMRegistry.gemma3_1B_qat_4bit`
    factory: LLMModelFactory
    ~0.8 GB. Fast. The safe choice on older hardware.

  MedGemma 4B
    repo: `mlx-community/medgemma-1.5-4b-it-4bit`
    factory: VLMModelFactory (custom `ModelConfiguration(id:)`)
    ~2.5 GB. Slower, better clinical summaries. This is the model the project
    is built around.

If `VLMModelFactory` rejects the 1.5 repo's config, check the repo's
`config.json` `model_type` against the factory's registry and fall back to
`mlx-community/medgemma-4b-it-4bit` (older conversion, same architecture).

Only ONE model may be resident in memory at a time on iOS. Loading a model
evicts the other from the container cache.

--------------------------------------------------
MODEL STORAGE
--------------------------------------------------

Do not accept the default Hugging Face cache location. On a sandboxed iOS app
it resolves into the container's Caches directory, and iOS is free to purge a
2.5 GB download from there under storage pressure.

Instead construct the client with a fixed cache directory under Application
Support, e.g.

    Application Support/Models/huggingface

and pass that client through `#hubDownloader(client)`. Mark the directory
`isExcludedFromBackup` so multi-gigabyte weights are not pushed into iCloud
backups. Use `HubCache.repoDirectory(repo:kind:)` to locate a single model's
files for the "downloaded?" check, the on-disk size, and deletion.

--------------------------------------------------
ARCHITECTURE
--------------------------------------------------

Follow ARCHITECTURE.md: protocols and plain models in `Domain/`, MLX-touching
implementations in `Services/`, composition in `App/AppDependencies`. No feature
code imports MLX.

New files:

  Domain/SummaryGeneration.swift
    `GeneratedSummary` — plain struct: `short`, `long`, `promptText`
      (`promptText` is the fully filled prompt; it is what `DIARY.prompt_text`
      must persist).
    `protocol SummaryGenerator` — one async throwing call taking the transcript,
      the `PatientProfile` and the prompt template, returning a
      `GeneratedSummary`. Must be cancellable.
    `SummaryGenerationError` — cases for: model not downloaded, unsupported
      device, load failure, output could not be parsed, cancelled. Each with a
      user-facing `errorDescription`.

  Domain/SummaryModelID.swift
    Framework-free identity of the two models: stable raw value for
    persistence, `displayName` ("Gemma 3 1B" / "MedGemma 4B"), `repoID`,
    approximate download size, and a short one-line description for Settings.
    The MLX `ModelConfiguration` mapping does NOT live here.

  Domain/ModelCatalog.swift
    `protocol ModelCatalog` — which model is selected, per-model download state
    (not downloaded / downloading with fraction / ready / failed), on-disk size,
    and actions to select, download, cancel and delete. Settings depends on this
    and nothing else.

  Domain/SummaryPromptTemplate.swift
    The verbatim template below as a constant, plus `fill(transcript:profile:)`
    substituting `{transcript}` and `{user_profile}`, plus a
    `PatientProfile` rendering into compact plain text for `{user_profile}`
    (name, age, weight, gender, health interests, health concerns — skip empty
    fields, never invent values). Pure, no MLX, unit-testable.

  Services/Intelligence/MLXSummaryGenerator.swift
    `actor`. Owns the container cache, the factory switch, generation and
    parsing. This is the only place that imports MLX*.

  Services/Intelligence/MLXModelCatalog.swift
    `ModelCatalog` implementation: HubClient with the fixed cache directory,
    download with progress, cancel, delete, size on disk, selection persisted
    in UserDefaults.

  Services/Intelligence/SummaryJSON.swift
    Pure parsing helpers: strip code fences, find the first balanced JSON
    object in a noisy completion, decode `{"short_summary", "long_summary"}`.
    Unit-testable without a model.

  Services/Intelligence/UnavailableSummaryGenerator.swift
    Mirrors the existing `Unavailable*` placeholders. Throws
    `.unsupportedDevice`. Used on the Simulator and in previews.

Wire both into `App/AppDependencies.swift` alongside `NoteStore`,
`AudioRecorder`, `Transcriber` and `ReminderScheduler`. No singletons.

--------------------------------------------------
PROMPT TEMPLATE (verbatim)
--------------------------------------------------

Store this exactly, placeholders included. Keep the "Return only this JSON"
line even though the output is parsed leniently — a prompt that agrees with the
expected shape produces better content.

You are a helpful medical assistant. You are helping me summarise an entry in my private voice diary. Based on my
transcript and my profile, write two summaries. Write both as if I wrote them:
first person, "I" and "my", throughout.

1. short_summary — one sentence. Examples of the style only, taken from other people's diaries. Never take a
   symptom, an activity or any other detail from them:
   "I slept more deeply and woke up feeling refreshed."
   "A mild headache appeared after lunch but eased by evening."
   "My energy dipped in the afternoon, so I took a short walk."
   "I felt calmer today and had steady energy throughout the day."
2. long_summary — one dense paragraph with the clinically useful detail: symptoms with their timing,
   duration and severity; what changed and in which direction; sleep, energy,
   appetite, pain, mood, movement; work, home and social context; anything new
   or different.

Rules:
- Record only what I said from the transcript below.
- Do not add or infer. No advice, no diagnosis, no causes. "I slept badly and
  felt flat" is correct; "my low mood is caused by poor sleep" is not.
- Neutral tone. Do not reassure, do not alarm.
- Ignore filler and false starts; leave out anything unintelligible.
- Plain language, no jargon, no markdown.

Return only this JSON and nothing else:
{"short_summary": "...", "long_summary": "..."}

TRANSCRIPT: {transcript}

Use my profile to judge what to foreground and how to pitch the language. Do not
mention it, and do not treat anything in it as something I said in this entry.

USER PROFILE: {user_profile}

The constant is the source of truth. Also upsert it into the PROMPT table via
`DemoDataSeeder` so the schema in `rules.txt` is honoured, but read it from the
constant at generation time.

--------------------------------------------------
GENERATION
--------------------------------------------------

One-shot, every time. No chat history, no system message, no state carried
between entries — two runs must never contaminate each other.

1. Fill the template with the transcript and the profile.
2. Load or reuse the selected model's container:
   `factory.loadContainer(from: #hubDownloader(client), using: #huggingFaceTokenizerLoader(), configuration:)`,
   factory chosen by model type. Cache the container; evict the other model
   when switching. Set `Memory.cacheLimit = 20 * 1024 * 1024` at app init.
3. Inside `container.perform`: build `UserInput(chat: [.user(filledPrompt)])`,
   `context.processor.prepare(input:)`, then `MLXLMCommon.generate(...)` with a
   low temperature (0.0–0.2) and a token cap around 800. Check the field names
   on `GenerateParameters` in the resolved checkout rather than guessing.
4. Accumulate the completion. Report coarse progress to the UI (a running token
   count or an indeterminate indicator) — do NOT show the raw JSON to the user.
5. Parse: strip any code fence, take the first balanced `{...}`, decode
   `short_summary` / `long_summary`. On failure, retry ONCE with a short
   corrective reminder appended. On a second failure, throw
   `.outputNotParseable`.
6. Return `GeneratedSummary(short:long:promptText:)`.

Never run this on the MainActor. Honour `Task.cancellation` between tokens.

SLOTTING IN
--------------------------------------------------

  transcribe -> reveal transcript -> write transcript file -> GENERATE SUMMARY

Changes:

  transcript file and `transcriptPath`, and leaves the summaries empty.

  previously ungenerated entry can be summarised later.

move generation into the record screen; the user should not be held on the orb
while a 4B model runs.

--------------------------------------------------
IMPLEMENTATION NOTES (added while building)
--------------------------------------------------

Answers to the questions this plan left open, and the two places the
implementation departs from it.

Packages:
- `MLXHuggingFace` is macros only. Its expansions reference `HuggingFace` and
  `Tokenizers`, so the app target must also link
  `huggingface/swift-huggingface` (product `HuggingFace`, 0.9.0) and
  `huggingface/swift-transformers` (product `Tokenizers`, 1.3.0). All three
  packages are pinned with `exactVersion`.
- mlx-swift resolves to 0.31.6 through mlx-swift-lm's own requirement.
- mlx-swift ships a `CudaBuild` prebuild plugin. Xcode asks once to trust it;
  from the command line pass `-skipPackagePluginValidation`.

Simulator:
- MLX DOES build and link for the iOS Simulator, so there is no need to
  condition the dependency. Only the runtime is unavailable, which
  `TangentApp` handles by injecting `UnavailableSummaryGenerator` under
  `#if targetEnvironment(simulator)`.

Downloads:
- `MLXLMCommon.resolve(configuration:from:useLatest:progressHandler:)` is
  public and downloads the model's files without loading them into memory,
  which is what Settings uses. It fetches exactly the patterns the factory will
  later want (`*.safetensors`, `*.json`, `*.jinja`), so generation finds
  everything already cached.

Departures from the plan above:
- The cellular warning became a size confirmation shown before ANY model is
  downloaded, naming the model and its size. 2.5 GB is worth confirming on any
  connection, and it avoids adding a network-path monitor.
- `SettingsView`'s `Form` had to be split into per-section computed properties;
  the whole body in one expression exceeded the type-checker's budget.
